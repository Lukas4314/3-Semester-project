\section{Discussion}\label{SEC:discussion}
\subsection{Communication}
MQTT is used for real-time data transfer for sound localisation, since it already was implemented on the Turtlebot3 for ROS2 communication. However, MQTT is not suited for real-time data transfer since it is a lightweight pub-sub messaging protocol. Through testing it was found that the required data rate for sending audio data was still lower than the maximum data rate of MQTT which made it appropriate to use in this project. 



\subsection{Movement control}

As seen in \cref{fig:path}, there is a deviation from the software to the physical world. This makes it almost impossible to fix since the issue lies in the given hardware. Giving a constant deviation to the motors was tested, but ultimately could not solve the problem since the deviation is too variable and can change depending on the type of floor. Therefore, the current setup does not account for deviation. This will, of course, add up and become exponentially worse the longer the robot is driving. However, this is still considered sufficient, since this project focuses on movement control and less on actual motor control.

\subsection{Sound localisation}
As seen in \cref{sec:testing} the system gets the best TDOA estimates when a filter is applied to GCC-PHAT, the weight is set to 0.8 and the samplesize is 2048 samples. However, even with this configuration the sound localisation system still leaves some to be desired. Importantly the system works, and with the right configuration it can achieve an angle error of about 16 degrees. It also does this within a reasonable time frame for it to be used for the purpose of this project. However, the high angle error effectively removes the possibility of precise movement control towards the sound source. 

One reason the angle error is so high, is the resolution achieved by using a sample rate of 16kHz as opposed to 44.1kHz or higher. The higher sample rate would allow for a more precise TDOA estimate which could improve the angle error. However the sample rate of 16 kHz was chosen as any higher could not be send to the computer in real time, and limited by hardware. 
Having 3 microphones where each smaples at 16 kHz, and each sample being 2 bytes, results in a data rate of 96 kbps, each clock cycle of the SPI, allows for a single bit to be transfered. Therefore to transfer 96 kbps, a clock speed of at least 768 kHz, is required. The current speed used is 3 MHz, which is sufficient for 16 kHz sample rate, and allowing time in between data trasnfers. A higher sample rate would therefore require a higher clock speed, which the Raspberry Pi can handle up to 35 Mhz \cite{BCM2711_Peripherals}, but the ESP32 can only handle up to 10 MHz \cite{ESP32_SPI_Slave}. Therefore a sample rate of 44.1 kHz would require a clock speed of at least 2.646 MHz, which is possible, but would leave less time in between data transfers, increasing the chance of data loss if the ESP32 cannot keep up with sending the data.

Another reason for the high angle error, could be the quality of the microphones. While the used microphones have synchronised clocks, they are still small, don't have amplifiers and not calibrated for use together. Using higher quality calibrated microphones that are preferably analog, with an external sound card to digitize the signal, could improve the timing accuracy and the clarity of the recorded sound. Both of these could lead to a better TDOA estimate and thus a lower angle error.

Additionally other methods than GCC-PHAT exist, like for example SRP-PHAT, which can be seen in \cite{SRP-PHAT}. However, SRP-PHAT is both more computationally heavy also only marginally better when using a large amount of microphones (15-256 microphones), as seen in other papers researching SRP-PHAT. Since this project only uses three microphones, GCC-PHAT was chosen as it is both less computationally heavy, works well enough with a low amount of microphones and is easier to implement.

For the triangulation, the TDOA values need to be very exact to match a specific point in the grid. Therefore, if the TDOA estimate is slightly off, the triangulation will return a point at the max distance (15 meters), which will be a very high distance error. Therefore, if the triangulation calculates a point thats more than a few meters away, the distance can't be used, because it means the point returned is a point very far away from the actual point. For this reason the ``come here'' command is used together with a distance, so the robot drives the calculated angle and the suggested distance by the user. This way the robot will move a distance that is far more accurate than the calculated distance from triangulation, because the user can estimate the distance. On the other hand, this also introduces the option of the robot moving a certain distance toward the user instead of stopping right in front of them.



\subsection{Talking as an interface}
The choice of voice commands as an interface for controlling the robot was made to allow for a more natural and intuitive way of interacting with the robot, whilst also allowing for hands-free operation. With the cababilities of the robot it was possible to understand the user. Although it was not perfect. The transcription accuracy was good in a quiet environment, but when the environment was noisy the accuracy dropped, resulting in missed commands. One of the biggest contributers to a noisy environment was the wheels on the robot itself. When the robot was moving the motors would whir loud enough to severely degrade the performance of the microphones. This was especially problematic when trying to call out the ``stop'' command.

Similarly to sound localisation, better hardware could improve the transcription accuracy. Using a higher quality microphone, that is designed for voice capture, could improve the clarity of the recorded audio. The current setup uses one of the microphones designed for sound localisation, but dedicating a fourth microphone to just transcription could allow for specific configuration and placement to optimize voice capture independently of the sound localisation microphones. However it is important that the final microphone array shares a clock, as it is needed to pinpoint when a person is saying the ``come here'' command. % Rune: hvorfor er det en god ide at have en microfon kun til transcipt? den er nødt til at have same klokke for at kunne finde "come" og så kan den da lige så godt blive brugt til GCC_PHAT

Specifically for mitigating noise from the robot itself, muffling the motors and wheels could help reduce the noise. Placing the microphones further away and switching them for either directional or noise cancelling microphones could help. This would likely need multiple microphones directed outwards.

To mitigate possible halucinations from noisy environments or unrelated speech, a VAD (Voice Activity Detection) system or wake word detection system could be implemented. This would ensure that the robot only listens for commands when it is being directly addressed, reducing the chance of misinterpreting background noise or conversations as commands. This could allow for more leeway in finding the exact words for commands.

For identification of commands, a less strict system could be implemented. Instead of requiring exact matches for commands by searching for keywords, a more flexible approach using NLP (Natural Language Processing) techniques could be used. This would allow the system to understand variations of commands or account for synonyms, making it more user-friendly and less rigid. A simple implementation of this using LLM (Large-Language-Model), such as ChatGPT prompts in addition to Whisper could be done, where the transcribed text is sent to LLM with a prompt asking if the text matches any commands in meaning, rather than exact words.

\subsection{AI model vs. Template based voice recognition}
Instead of using an AI model like Whisper, a template based voice recognition system could have been implemented. This could possibly have made the transcription on the Raspberry Pi possible, however it would potentially make communication with a PC obsolete. A template based system would also be more difficult to expand in the future, as it would require new templates for new commands. Using an AI like Whisper is easier to implement and more flexible. Whisper is also better suited for an environment like a workshop with different sounds and works with any human.
