\subsection{MQTT}
MQTT is used for real-time data transfer for sound localisation, since it already was implemented on the Turtlebot3 for ROS2 communication. However, MQTT is not suited for real-time data transfer since it is a lightweight pub-sub messaging protocol. Through testing it was found that the required data rate for sending audio data was still lower than the maximum data rate of MQTT which made it appropriate to use in this project. 



\subsection{movement control}

As seen in the plotted path, there is a deviation from the software to the physical world. This makes it almost impossible to fix since the issue lies in the given hardware. Giving a constant deviation to the motors was tested, but ultimately could not solve the problem since the deviation is too variable and can change depending on the type of floor. Therefore, the current setup does not account for deviation. This will, of course, add up and become exponentially worse the longer the robot is driving. However, this is still considered sufficient, since this project focuses on movement control and less on actual motor control.

\subsection{Sound localisation}
The sound localisation system leaves some to be desired. Importantly the system works, and with the right configuration it can achieve an angle error of about 16 degrees. It also does this within a reasonable time frame for it to be used for the purpose of this project. However, the high angle error effectively removes the possibility of precise movement control towards the sound source. 

One reason the angle error is so high, is the resolution achieved by using a sample rate of 16Khz as opposed to 44.1Khz or higher. The higher sample rate would give allow for a more precise TDOA estimate which could improve the angle error. However the sample rate of 16 Khz was chosen as any higher could not be send in real-time over SPI to the Raspberry Pi. An increase in sample rate would as such require better hardware.

Another reason for the high angle error, could be the quality of the microphones. While the used microphones are synchronised in the clocks, they are still small, don't have amplifiers and not calibrated for use together. Using higher quality calibrated microphones that are preferably analog, with an external sound card to digitize the signal, could improve the timing accuracy and the clarity of the recorded sound. Both of these could lead to a better TDOA estimate and thus a lower angle error.

Additionally other methods than GCC-PHAT exist, like for example SRP-PHAT, which can be seen in \cite{SRP-PHAT}. However, SRP-PHAT is both more computationally heavy also only marginally better when using a large amount of microphones (15-256 microphones), as seen in other papers researching SRP-PHAT. Since this project only uses three microphones, GCC-PHAT was chosen as it is both less computationally heavy, works well enough with a low amount of microphones and is easier to implement.

\subsection{Talking as an interface}
The choice of voice commands as an interface for controlling the robot was made to allow for a more natural and intuitive way of interacting with the robot, whilst also allowing for hands-free operation. With the cababilities of the robot it was possible to understand the user. Although it was not perfect. The transcription accuracy was good in a quiet environment, but when the environment was noisy the accuracy dropped, resulting in missed commands. 

Similarly to sound localisation, better hardware could improve the transcription accuracy. Using a higher quality microphone, that is designed for voice capture, could improve the clarity of the recorded audio. \subsection{AI model vs. Template based voice recognition}
Instead of using an AI model like Whisper, a template based voice recognition system could have been implemented. This could possibly have made the transcription on the Raspberry Pi possible, however it would potentially make communication with a PC obsolete. A template based system would also be more difficult to expand in the future, as it would require new templates for new commands. Using an AI like Whisper is easier to implement and more flexible. Whisper is also better suited for an environment like a workshop with different sounds and works with any human.
