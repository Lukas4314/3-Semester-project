The overall system architecture is divided into three main components: the PC, the Raspberry Pi onboard the Turtlebot, and the ESP32 microcontroller. Each component has its own layered architecture. The layers are designed to interact only with the layer directly above or below them, ensuring modularity and clear separation of responsibilities. The 4 layers consist of a physical interface layer that should handle direct communication with physical components, a communication layer that manages data transfer between devices and processes, a data processing layer that handles mathematic operations, data packing and transcription, and finally an application layer that interprets processed data and makes decisions based on it.

\subsection{PC}
The architecture of the PC is illustrated in \cref{fig:PC_system_overview}. It spans 3 layers. The lowest layer, the communication layer, handles communication via an MQTT client that communicates with the MQTT broker hosted on the Turtlebot. The client has 2 way communication with the broker, subscribing to the audio data provided by the ESP32 and publishing positional commands for the Turtlebot. An important aspect the client handles is to duplicate one of the audio streams into 2 queues, as one has to be used for transcription while the other is used with the other 2 streams for sound localisation.

The middle layer, the processing layer, processes the audio data. OpenAI's Whisper model is used for transcription, while the GCC-PHAT algorithm is used for sound localisation. Using the algorithm 3 TDOA (Time Difference of Arrival) values are calculated with which triangulation is performed to estimate the sound source's position. 

The transcribed text is then interpreted for commands on the application layer, and any identified command is translated into a positional command for the robot. If the command ``come here'' is given, the triangulated position is used to calculate a turn and drive command to move the Turtlebot towards the speaker's location.

\subsection{Turtlebot and Raspberry Pi}
The Raspberry Pi similarly has a processing and communication layer. However as the robot also has to control the motors, an additional physical interface layer is needed, while the application layer is not needed. The architecture of the Raspberry Pi is illustrated in \cref{fig:RPI_system_overview}.

From the top, Layer 2 is the processing layer. Here, a ROS2 node gets positional commands from the mosquitto client in the communication layer and translates them into velocity commands that the turtlebot can interpret. Then the messages are published on a ROS2 topic. Furthermore, joint states from the Turtlebot are also read on a ROS2 topic and used for a P-regulator to ensure the motors are moving the correct speed.

Layer 2 is the communication layer. Besides the mosquitto client that subscribes to positional commands from the PC, it also hosts the MQTT broker that all the clients are connected to. Besides the MQTT infrastructure, the layer also handles communication with the Turtlebot's OpenCR board via UART (Universal Asynchronous Receiver-Transmitter). The velocity commands published on the ROS2 topic in the processing layer are picked up by the Turtlebot node, which forwards them via UART to the OpenCR board for motor control, as well as reading joint states from the board and publishing them on a ROS2 topic for the processing layer to use.

The lowest layer, Layer 1, is the physical interface layer. This is handled completely onboard the OpenCR board and is responsible for low-level motor control. The board handles the velocity commands sent from the Raspberry Pi and translates them into PWM (Pulse Width Modulation) signals for the motors to execute the desired movement.

\subsection{ESP32}
The last device is the ESP32 microcontroller. As no application layer is needed here, the architecture only spans the 3 lowest layers, as illustrated in \cref{fig:ESP32_system_overview}.

On the physical interface layer, the ESP32 interfaces with the 3 microphones using the I2S protocol.

On the communication layer, the ESP32 reads the audio data from the I2S RMA buffers and provides it for processing.
