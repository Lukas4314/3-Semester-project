\section{Sound Recording}
\label{sec:sound_recording}
For sound recording, three I2S (Inter-Integrated-Circuit-Sound) MEMS (Micro-Electro-Mechanical-System) microphones are used \cite{DFRobot_Fermion_I2S_MEMS_Microphone}. Their key advantage is the ability to share the same clock, ensuring samples are taken simultaneously, which is essential for comparing phase differences between signals. Since the microphones use I2S, a compatible interface is required. The Raspberry Pi has only one I2S interface, which can handle two microphones by utilizing the left and right channel of stereo. To support three microphones, an ESP32 microcontroller is employed, as it provides two I2S interfaces, enabling up to four microphones. In this setup, three microphones are used, resulting in one stereo interface and one mono interface.

The I2S protocol requires three lines \cite{ESP32_I2S}:

SCK (Serial Clock): Synchronizes data transmission.

WS (Word Select): Selects between left and right channels.

SD (Serial Data): Carries the actual audio data.

Additionally, each microphone requires connections for 3.3V power, ground (GND), and an L/R pin to configure whether it uses the left or right channel.

To synchronize all three microphones, one I2S interface on the ESP32 is configured as the master and the other as a slave. Their clock lines (SCK and WS) are connected, ensuring both interfaces use the same clock. This guarantees simultaneous sampling across all microphones, enabling accurate phase comparison.

When the microphones transmit data to the ESP32, it is written directly into a DMA (Direct Memory Access) buffer. This allows efficient data transfer without continuous CPU intervention. By supplying multiple DMA buffers to an I2S interface, data can be streamed into one buffer while the CPU processes the previous one.

The microphone resolution is set to 16 bits, meaning each sample is represented by two bytes. The master clock drives the WS line, and each microphone, configured as left or right, outputs its data starting with the most significant bit. A higher sample rate increases the number of samples available for phase-difference calculations, potentially improving precision. However, it also increases the data volume the ESP32 must process and transmit. If the ESP32 cannot process and send data before the next batch arrives, DMA buffers overflow, leading to data loss. In this configuration, an unhandled overflow results in the loss of 960 samples, the size of a DMA buffer, causing a misalignment in subsequent buffers and corrupting phase calculations.

The ESP32 provides a callback mechanism \cite{ESP32_I2S} to handle DMA buffer overflows via an ISR (Interrupt Service Routine). This callback must be placed in IRAM (Instruction RAM), and any associated data objects must reside in DRAM (Data RAM). A counter can be implemented to track filled and overflowed buffers, incrementing in both scenarios, and used to timestamp the data. To minimize overflow risk, the ESP32’s two cores are utilized: one core handles I2S data acquisition and timestamping, while the other manages data transmission to the Raspberry Pi.

\subsection{Communication with the Raspberry Pi}
The Raspberry Pi’s hardware can only function as the master on an SPI (Serial Peripheral Interface) bus, requiring the ESP32 to operate in slave mode \cite{BCM2711_Peripherals}. Since the ESP32 determines when data is ready to send, a GPIO pin is used as a “data ready” signal to the Raspberry Pi. SPI also employs DMA buffers. When the ESP32 prepares data for transmission, it configures separate transmit and receive buffers and asserts the “data ready” pin. SPI callbacks indicate when buffers are loaded and when a transaction is complete, allowing the pin to be toggled accordingly. On the Raspberry Pi, a rising-edge interrupt on the “data ready” pin triggers the SPI transaction to receive the data. This approach lets the ESP32 control the timing of data transfers despite being the SPI slave.

\subsection{3D-Printed Microphone Mount}
To get the best performance out of the microphones, a 3d-printed mount was created that put them in an equilateral triangle away from the center of the robot. By having the microphones on a 3d printed mount, the distance could be set precisely and the micrphone grill could be directed upwards towards the user. This reduces echo from the ground and allows users to speak directly into the grill from any direction, as long as they are above the robot. The mount is shown in \cref{fig:microphone_mount}.
