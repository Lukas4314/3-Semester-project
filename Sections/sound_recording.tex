\section{Sound Recording}
For soundrecording 3 I2S Mems microphones are used, as they have the possibility to share the same clock, ensuring that the samples are taken at the same time, which later can be compared to find the phase difference between the signals. Since the microphones use I2S, an interface to interact with the microphones are needed, but unfortunately the Raspberry Pi only has one I2S interface. A single I2S interface can be used to handle 2 microphones, by using both the left and right channels which are normally used for stereo sound. To be able to use more than 2 microphones an ESP32 is used, as it has 2 I2S interfaces, allowing it to handle up to 4 microphones, but in this case only 3 are used, resulting in 1 stereo and 1 mono. The ESP32 also has the ability to use WiFi and therefore can use MQTT to send the recorded audio directly to the computer, where processing can be done.
The I2S protocol requires 4 lines:
SCK: Serial Clock, used to synchronise the data transmission.
WS: Word Select, used to choose whether the left or right channels is being transmitted.
SD: Serial Data, the actual audio data being transmitted.

These 3 channels are required for the I2S communication. 3 additional wires are used for the microphones which include 3v3 (3.3 Volt), GND (Ground) and a L/R (Left/Right) pin which is used to choose whether the microphone uses the left or right channel.

Configuring one of the I2S interfaces on the ESP32 to be master and the other to be slave, the clock lines can be connected, that being SCK and WS, allowing both interfaces to use the same clock. This ensures that the samples are taken at the same time, allowing for phase comparison between all 3 microphones.

When the microphones send data to the specified data pins on the ESP32, the data is written directly into a DMA (Direct Memory Access) buffer, allowing for efficient data transfer without the need for CPU intervention. The ESP32 has a DMA controller which handles the transfer into the buffer.
By supplying multiple DMA buffers to a I2S interface, the data can be streamed into one of the DMA buffers, while the CPU reads the previous buffers, and sends the data via MQTT to the computer.

The resolution of the microphones can be set, and for this use case is set to 16 bits, meaning that each sample is represented by 2 bytes. When the master outputs its clock, the transmitters (the microphones), listen to the WS line, and depending on whether it is configured as left or right, outputs the most significant bit first, followed by the remaining bits.

By having a higher samplerate it would be possible to increase the amount of samples which can be used to determine the phase difference between the signals. This would result in more precise calculations, but would also increase the amount of data needed to be processed by the ESP32. If the ESP32 is not fast enough to proccess the data and send it to the computer before the next data arrives, the DMA buffers would overflow resulting in loss of data. The loss of data would correspond to the size of the buffer, so in this case it would be 960 samples. A smaller samplerate would reduce the amount of data needed to be processed, but would also reduce the precision of the phase calculations. If an overflow would happen and it is not handled the next buffer would be counted as the previouss buffer and the sound samples would therefor be off by 960 samples. Later when the phase is calculated it too, would be off by 960. The ESP32 offers a solution of a callback which can be set and called when the DMA buffers overflow. It takes place in a ISR, and the ESP32 therefore requires the callback to be placed in the IRAM (Instruction random access memory), and any object passed as the arguments to the function, must be placed in the DRAM, (Data RAM). Both can be set by using the attribute IRAM\_ATTR and DRAM\_ATTR when creating the function, and object for the I2S Interface. The I2S interface can therefore have a counter which increases every filled DMA buffer, and when a DMA buffer overflows. To decrease the chance of a DMA buffer overflowing, the 2 cores of the ESP32 are utilized, making 1 core handle the I2S data recieving, and add the counter, and the other core handle the transfer of the data to the computer, for communicating between the cores an array of 10 buffers for data are creating globally and a queue holding the index of the current DMA buffers is used to tell the other core which buffers are ready. By making the queue one smaller than the amount of global buffers, it ensures the "writer" core will not overwrite any data before it has been sent to the computer.
For sending the data from the ESP32 to the computer, the wifi module on the ESP32 was first used and sending directly usin MQTT, but it wsa found that this approach introduced a varying latency and inconsistency making the queue randomly overflow. To solve this issue, SPI is used between the ESP32 and the Raspberry Pi, where the Pi then can send it over MQTT to the computer. This gives a more consistent data transfer and move the wireless communication to the Raspberry Pi which has a more stable wifi connection.
The hardware on the Raspberry Pi can only work as the master on the SPI bus, and therefore the ESP32 needs to be in slave mode. Since it is the ESP32 that knows when the data is ready to be sent, a GPIO pin is used as a "data ready" signal form the ESP32 to the Raspberry Pi. The SPI also works with the DMA buffers and, therefore when the ESP32 wants to use SPI to send data, it will load 2 buffers into the DMA, 1 for transmit and 1 for recieve, and then set the "data ready" pin high. The SPI offers a callback which is called when the ESP32 has loaded the DMA buffers, and is ready for a transaction, and another callback when the transaction is complete. In this callback the "data ready" pin can be set high and low respectively. On the Raspberry Pi an event can be set on the "data ready" pin on the rising edge, and when the event is triggered the Raspberry Pi can start the SPI transaction to recieve the data from the ESP32. This method makes it so the ESP32 is in charge of when the data is sent, despite being the slave in the SPI bus.
